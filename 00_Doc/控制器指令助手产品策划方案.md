# 控制器指令助手产品策划方案

> 状态：产品策划评审稿；GitLab 数据源与取消应用账号管理已确认，应用开发尚未启动  
> 创建：2026-09-21；修订：2026-09-28  
> 暂定用户端名称：**控制器指令助手**  
> 数据源：**本地 GitLab 公开指令数据仓库的 main 分支**

本次修订采纳用户的两项决定：从本地 GitLab 的公开仓库获取数据；研发身份、写入权限和 main 分支管理交给 GitLab，软件不再建设账号管理、登录或独立发布后台。参数化录入、中文查询、组帧和离线使用继续保留。

## 1. 执行摘要

产品定位为**GitLab 管理的指令知识库 + 完全本地运行的查询与组帧客户端**，可以与现有串口测试工具、网络诊断工具衔接：

- 研发把“指令的用途、适用产品、固定字节、可调参数、编码方式、校验规则、风险等级”录入为结构化模板。
- 售后用中文搜索意图，选定产品/型号/固件版本，填入“通道=1、亮度=255”等参数，由软件生成完整指令。
- 本地 GitLab 公开数据仓库是权威数据源；搜索、填参和组帧全部在 Windows 客户端本地完成，售后同步无需账号或令牌。
- 研发通过本地录入工具导出结构化数据，使用 GitLab 现有身份提交分支；校验和审核通过后合并到受保护的 main。
- 客户端保存“最后一份已验证、已发布”的本地快照，离线时仍能查询和组帧。
- 同步在后台执行；用户只看到“已同步 / 可更新 / 同步失败，已保留旧版”。

开发规模比原先自建账号和发布服务的方案更小。主要工作集中在指令模型、研发录入工具、本地检索、组帧和可靠同步：

1. 建立能覆盖 HEX、ASCII、大小端、枚举、缩放、校验的可维护指令模型。
2. 确保任何售后可见的指令都经过研发审核和黄金样例验证。
3. 中文搜索不把相似但不兼容的协议/型号混在一起。
4. 同步失败或 main 出现无效数据时，客户端保留本地可用版本；一次同步的所有文件必须来自同一个提交。

## 2. 产品定位

### 2.1 要解决的问题

| 当前问题 | 产品解法 |
|---|---|
| 协议散落在 Word/Excel/代码/聊天记录中 | 统一的版本化指令知识库 |
| 售后只知道“我要设亮度”，不知道命令字 | 按中文意图、别名、问题现象搜索 |
| 手工替换字节容易改错位置或大小端 | 结构化参数表单 + 确定性组帧 |
| 同一指令对不同型号/固件不同 | 产品、型号、硬件、固件范围适用性门禁 |
| 不知道谁改过协议库 | GitLab 提交历史、合并请求、评审记录和变更说明 |
| 离开公司局域网后无法查询 | 从 main 下载并校验的本地数据快照，离线可用 |

### 2.2 不是什么

- 首版不是设备远程控制平台，不直接向控制器发送指令。
- 不是任意脚本执行器，研发不能上传可在售后电脑上执行的代码。
- 不代替完整协议文档；它存放可执行的结构化知识和必要说明。
- 账号和主分支权限直接使用 GitLab 的既有能力，客户端无需额外维护身份系统。

### 2.3 与现有软件的边界

- 现有“串口测试工具”保留已验收的原始字符串指令模型和测试统计。
- 新的“控制器指令助手”使用参数化模板、语义检索和发布治理。
- 首版集成仅为“复制 HEX/ASCII”或“导出已解析的静态指令 JSON”；不改动现有工具核心。
- 现有 132 条指令可作为迁移原料，但必须由研发补录参数定义、适用范围和测试向量，不能自动当成已审核数据。

## 3. 维护与查阅分工（由 GitLab 管理）

### 3.1 分工

| 人员 | 使用入口 | 负责的事情 |
|---|---|---|
| GitLab 管理员 | 本地 GitLab | 配置公开读取、项目成员、main 保护、Runner 和备份 |
| 协议维护者（研发） | 本地录入工具 + GitLab 分支 | 填写参数化指令、测试向量，导出数据并提交合并请求 |
| 协议审核者/维护者 | GitLab 合并请求 | 检查协议和适用性、确认 CI 结果，决定是否合并到 main |
| 查阅者（售后） | Windows 指令助手 | 匿名同步 main，离线查询、填参、组帧、复制和导出 |

### 3.2 客户端无需账号管理

- 客户端没有登录、注册、共享维护密码、用户管理或应用角色数据库。
- 售后使用的客户端不持有 GitLab 写入凭据；公开读取也不内置研发令牌。
- 研发录入工具只修改本地草稿并导出文件，提交和合并使用研发已有的 GitLab 工作流。
- 谁能修改正式数据由 GitLab 项目权限和 main 保护决定，不依赖本地按钮是否隐藏。
- 本地草稿与 main 同步所得的正式快照分开保存；编辑草稿不会改变售后正在使用的正式库。

GitLab 的公开项目及公开仓库文件支持匿名读取。部署时还需确认本地实例允许此项目匿名访问仓库和所用 API，不能把需登录的 Internal 可见性当作 Public。[GitLab 可见性说明](https://docs.gitlab.com/user/public_access/)、[仓库文件 API](https://docs.gitlab.com/api/repository_files/)。

## 4. 核心用户旅程

### 4.1 售后：用中文找到并生成指令

1. 首次打开或更换现场时，选择产品系列、控制器型号、固件版本和协议。
2. 输入“设置3号通道亮度255”、“查设备IP”或“关闭光源”。
3. 客户端先用产品/版本做硬过滤，再用中文全文、别名、同义词和本地语义向量混合排序。
4. 结果显示指令用途、适用范围、风险等级、参数摘要和来源版本。
5. 选中指令后，软件将语句中识别到的3和255作为**建议填入值**，仍要求用户在明确的“通道”和“亮度”框中确认。
6. 实时生成完整 HEX/ASCII，同时显示字段拆解、值域、校验和一条人类可读解释。
7. 用户复制指令，或导出为现有串口测试工具可读的静态条目。

安全原则：搜索可以帮用户找到和预填参数，但不得在未选定产品/版本时静默生成“看起来可用”的指令。

### 4.2 研发：创建并发布参数化指令

1. 打开本地研发录入工具，基于当前 main 快照选择产品/协议并创建本地草稿，无需应用登录。
2. 填写中文名称、用户意图、别名、适用型号/固件、使用说明和风险等级。
3. 在“帧编辑器”中按顺序放入固定字节、参数字段和计算字段。
4. 为每个参数定义类型、字节长度、大小端、范围、单位、默认值、枚举项、显示提示和售后是否可调。
5. 录入至少一组“参数输入 -> 预期完整字节”黄金测试向量。
6. 执行本地校验，预览边界值结果，导出标准 JSON、版本清单和测试向量。
7. 用 GitLab 分支提交文件并创建合并请求；CI 校验数据，维护者查看差异和协议依据，通过后合并到 main。
8. 售后客户端下次连上局域网时自动同步该 main 提交，保存本地快照；同步失败继续使用原有版本。

研发也可直接使用 GitLab Web IDE 或熟悉的编辑器修改 JSON。可视化录入工具的价值是降低填写参数规则的门槛，并即时看到完整帧；它无需管理 GitLab 登录或自行推送。

## 5. 研发应该如何填写指令

### 5.1 一条指令的数据分组

| 分组 | 关键字段 |
|---|---|
| 身份 | 指令ID、中文名称、命令字、所属协议、功能分类 |
| 适用性 | 产品系列、型号、硬件范围、固件版本范围、传输通道 |
| 检索知识 | 用户意图、中文别名、常见问法、现象、关键词、说明 |
| 请求帧 | HEX/ASCII、固定段、参数段、计算段、转义/终止符 |
| 参数 | 变量名、中文标签、输入类型、编码、大小端、长度、值域、单位、默认值 |
| 计算规则 | 长度、XOR/SUM/CRC 类型、计算范围、初值、输出字节序 |
| 回复 | 回复模板、成功/错误标志、可提取字段、超时建议 |
| 使用风险 | 只读/普通设置/高风险、警告文案、是否二次确认；不向售后分发的内容不放入公开仓库 |
| 治理 | 数据负责人、内容版本、废弃替代项；提交者、合并者和评审理由由 GitLab 记录 |
| 验证 | 正常值、上/下边界、非法值和已知回复测试向量 |

### 5.2 帧模板不用“手工说明第几字节”作为唯一依据

界面可以显示“起始字节/长度”，但内部建议用**有顺序的帧段**表示，避免增加一个字段后所有位置都要人工修改：

- `fixed`：固定字节或固定 ASCII。
- `parameter`：由售后表单填写的参数字段。
- `computed`：长度、BCC、CRC 等由系统计算的字段。

每个段的起始位置由系统根据前面段自动计算，界面再以一行字节地图展示给研发确认。对特殊协议可使用高级显式偏移，但发布前必须通过重叠、空洞和长度校验。

### 5.3 亮度指令示例

下例仅演示产品模型，实际协议以研发审核和黄金向量为准。

| 字节范围 | 类型 | 定义 |
|---|---|---|
| 0 | 固定 | `CA`，帧头 |
| 1 | 固定 | `01`，设置亮度命令字 |
| 2 | 参数 | `channel`，无符号1字节，范围1~40 |
| 3~4 | 参数 | `brightness`，无符号16位大端，范围0~999 |
| 5 | 计算 | 对0~4字节逐字节 XOR |

售后界面只显示：

- 通道：`1`
- 亮度：`255`

预览区显示：

```text
CA 01 01 00 FF 35
帧头=CA | 命令=01 | 通道=1 | 亮度=255(00 FF) | BCC=35
```

这样软件知道可调的不是一段随意文字，而是有名称、值域、编码和位置的字段。

### 5.4 首版建议支持的参数类型

- 无符号/ 有符号整数：8/16/32位，大端/小端。
- 布尔和枚举：开/关、模式选择。
- 定长 ASCII、ASCII 十进制数字、ASCII 十六进制数字。
- 原始 HEX：限定长度，仅对已审核并明确允许调整的参数开放。
- 缩放与偏移：例如用户输入1.5ms，协议写1500。
- 计算字段：XOR8、SUM8/SUM16、已明确参数的 CRC16。

首版不允许研发填写 JavaScript/Python 等任意执行脚本来组帧。无法用受控规则表达的特殊协议先保留为带说明的静态示例，或暂不纳入公开数据；后续通过产品发版增加经过测试的组帧算子。

## 6. 指令生命周期与发布门禁

```text
本地草稿 -> GitLab 工作分支 -> 合并请求 + CI 校验 -> 维护者合并 main
                                  |                   |
                              修改后重审          客户端同步快照
```

main 是正式数据入口。修改已发布指令时提交新分支和合并请求，Git 历史保存旧版本；废弃指令在正式数据中标明原因和替代项。客户端只同步 main，不读取工作分支或未合并内容。

### 6.1 main 分支管理建议

| 设置 | 建议 |
|---|---|
| 目标分支 | main，受保护 |
| Allowed to push and merge | No one，禁止直接推送 |
| Allowed to merge | Maintainers，由维护者完成审核和合并 |
| Force push | 关闭 |
| 合并检查 | 启用 Pipelines must succeed；每个 MR 都运行必需校验，不能把跳过校验视为成功 |
| 合并前内容 | 分支更新到最新 main 后重新校验，维护者确认待合并版本及测试结果 |

保护分支控制写入和合并权限，指令数据是否正确仍由自动校验和协议评审共同确认。应检查是否有更宽松的通配分支规则同时匹配 main。[GitLab 分支保护规则](https://docs.gitlab.com/user/project/repository/branches/protection_rules/)、[流水线合并检查](https://docs.gitlab.com/user/project/merge_requests/auto_merge/)。

基础流程可以用 Developer 提交分支、Maintainer 审查后合并。GitLab Free 的 Approval 本身不能强制阻止无审批合并，因此基础方案不依赖付费的强制审批或 CODEOWNERS 功能；具体设置按本地 GitLab 版本核对。[GitLab 合并请求审批](https://docs.gitlab.com/user/project/merge_requests/approvals/)。

### 6.2 发布前自动校验

- 指令ID唯一，适用型号和固件范围不矛盾。
- 帧段无重叠、无非预期空洞，固定长度和最终长度可计算。
- 默认值在值域内，枚举无重复编码，大小端已选择。
- 校验算法和覆盖范围完整，不能用“计算全帧”这种循环定义。
- 至少一个黄金向量通过；数值参数至少自动检查上下边界。
- 面向售后的条目必须有中文意图、使用说明和风险等级。
- 已废弃指令必须标明原因，有替代项时指向替代项。
- 版本清单列出的文件、大小和 SHA-256 与提交内容一致；不允许把本地草稿或未支持的 schema 混入正式数据。

上述规则由同一套验证器供本地录入工具和 GitLab CI 使用。CI 只检查提交内容，不另行推送生成文件到 main；研发导出时生成对应清单，避免额外发布提交和自触发循环。

### 6.3 风险分级

| 级别 | 示例 | 售后策略 |
|---|---|---|
| L0 只读 | 读取版本、状态、当前参数 | 可查看和组帧 |
| L1 可恢复设置 | 亮度、开关、常规模式 | 显示影响，可复制 |
| L2 高风险设置 | 网络参数、保存Flash、重启 | 按发布策略纳入或排除；纳入后显示警告和二次确认 |
| L3 破坏性/工厂 | 恢复出厂、擦除、校准写入 | 首版不放入公开数据仓库，保留在研发现有受限资料中 |

公开仓库中的内容对可访问该仓库的人开放，客户端没有个人权限过滤。仅从 main 的界面结果中隐藏一条指令，不能阻止别人读取仓库的其他分支或历史；不应公开的资料从一开始就不进入这个公开仓库。[GitLab 公开项目说明](https://docs.gitlab.com/user/public_access/)。

## 7. 中文检索与本地语义查询

### 7.1 推荐的混合检索管线

1. **适用性硬过滤**：产品、型号、固件、协议和指令可用状态。
2. **结构化精确命中**：指令ID、命令名、标签、别名。
3. **本地全文检索**：意图、说明、常见问法、参数标签，兼顾拼音和模糊匹配。
4. **本地语义检索**：内置可离线运行的小型中文文本向量模型，按意图相似度补充召回。
5. **可解释排序**：精确别名和适用性分数高于纯语义相似，结果显示“为什么匹配”。

语义搜索不调用外网 API，不向任何云端上传查询或协议内容。语义模型和索引随客户端/数据快照本地分发。

### 7.2 检索验收不能只看“搜得出”

由售后和研发共同建立至少 50~100 条真实问法的标准集，包括口语、同义词、错别字和无结果样本。MVP 建议目标：

- 适用指令 Top 3 召回率 >= 95%。
- 已选定产品/版本时，不兼容指令误出现为可用结果：0。
- 无可用结果时明确说“暂无已发布指令”，不由 AI 自行编造字节。

## 8. 完全本地运行与局域网同步

### 8.1 定义“完全本地运行”

- 断开局域网和互联网后，已同步的指令可搜索、查看、填参、组帧和导出。
- 搜索索引、语义模型、参数校验、校验和计算全部在客户端进程内完成。
- 售后在线同步和离线查阅都无需应用登录，已同步的知识库不依赖 GitLab 持续在线。
- 研发可以离线编辑本地草稿；更新正式库须回到 GitLab 提交和合并流程。

### 8.2 同步协议

数据通过本地 GitLab 的公开仓库获取，部署范围仍为局域网。客户端通过 HTTPS 读取 GitLab 现有接口，无需安装 Git、克隆完整历史或配置令牌。推荐流程：

1. 查询 main 的当前提交 SHA，与本地已激活快照的 SHA 比较；一致时无需重新下载。
2. 有变化时，固定本次目标提交 SHA；后续所有文件使用 `ref=<该 SHA>`，不逐个使用动态的 `ref=main`。
3. 从这个提交读取 manifest：内容版本、schema 版本、最低客户端版本、文件清单、大小和 SHA-256。
4. 把清单内所需文件下载到本地临时目录；同步期间 main 又变化也不影响本次快照的一致性。
5. 检查下载完整性、schema 兼容性、指令引用、参数规则和黄金测试向量，构建本地检索索引。
6. 全部通过后原子激活新快照，保存来源项目、提交 SHA 和同步时间，旧快照至少保留一份。
7. 下载或校验失败继续使用旧快照；没有旧快照的首次同步失败则提示“暂无本地数据”，不显示虚假的同步成功。
8. 当前打开的组帧表单固定其数据版本；新库就绪后再重新打开或明确切换，不把旧参数套入新模板。

GitLab 的分支 API 可查询公开仓库的分支提交，文件 API 可按分支、标签或提交读取；这里采用提交 SHA 来固定一次同步的内容。[分支 API](https://docs.gitlab.com/api/branches/)、[文件 API](https://docs.gitlab.com/api/repository_files/)。

技术接口示意（项目 ID、路径和主机在部署时配置）：

```text
GET /api/v4/projects/<project_id>/repository/branches/main
GET /api/v4/projects/<project_id>/repository/files/catalog%2Fmanifest.json/raw?ref=<commit_sha>
```

MVP 把 main 中提交的普通数据文件作为同步源，不依赖会过期的 CI Job Artifacts 或另建下载服务。CI 用于校验；正式数据随 main 提交保存。GitLab 登录页、404、请求失败均按同步失败处理。

用户可见状态建议只有：

- 绿色：已同步，数据版本 `2026.09.28.1`，上次成功时间。
- 黄色：当前离线，正在使用本地版本。
- 蓝色：发现新版/正在同步。
- 红色：同步失败，**本地可用版本已保留**。

### 8.3 并发修改与回退

- 多名研发修改同一数据时，沿用 GitLab 合并请求的冲突处理；本地草稿记录基础提交，提交前与最新 main 核对，避免整库覆盖别人已合并的修改。
- 正式库出错时，维护者通过 revert 合并请求恢复正确内容，重新校验并合并，产生新的 main 提交；不通过 force push 重写发布历史。
- 客户端根据提交 SHA 变化发现更新，不仅比较显示版本号大小，确保恢复旧内容的新提交也能正常同步。
- 本地可回退到上一份已验证快照，状态明确显示正在使用的版本和来源，不把本地回退伪装成已与 main 一致。

### 8.4 建议的数据仓库结构

```text
controller-command-catalog/
├── README.md                     # 维护流程和字段说明
├── catalog/
│   ├── manifest.json             # 数据版本、兼容版本、文件清单及哈希
│   ├── products.json             # 产品、型号、固件和协议适用性
│   ├── commands.json             # 参数化指令模板
│   └── synonyms.json             # 中文别名及同义词
├── schemas/
│   └── catalog.schema.json       # 数据格式定义
├── tests/
│   └── golden_vectors.json       # 参数输入与完整预期帧
├── tools/                        # 数据验证器
└── .gitlab-ci.yml                # MR/main 数据校验
```

清单只描述数据和测试所需文件；验证器、CI 配置不会作为售后数据包中的可执行内容下载。提交 SHA 由 GitLab 响应提供并由客户端记录，无需把提交自身的 SHA 写回清单。

## 9. 信息架构与主要页面

### 9.1 售后模式

1. **首页/搜索**：产品上下文、大搜索框、最近使用、收藏、同步状态。
2. **搜索结果**：按适用性、功能、风险等级过滤，显示匹配原因。
3. **指令详情/组帧**：中文说明、参数表单、完整帧、字段拆解、复制/导出。
4. **收藏与历史**：保存指令ID和参数，不保存一份脱离版本的无来源字节串。
5. **数据与帮助**：当前内容版本、上次同步、本地可用状态、问题反馈。

### 9.2 研发本地录入工具

1. **本地草稿**：打开 main 快照、创建或复制条目，显示基础提交和修改状态。
2. **指令编辑器**：基本信息、适用性、帧段、回复、风险、检索知识。
3. **帧可视化编辑器**：字节地图、参数定义、边界值预览、即时生成。
4. **测试向量**：参数集、预期帧、实际帧、通过/失败。
5. **校验与导出**：字段级差异、影响型号、完整校验结果，导出提交所需文件。
6. **GitLab 协作入口**：打开对应仓库或 MR 链接，审核、合并和问题讨论在 GitLab 中进行。

无需在软件中重建 GitLab 的待审核列表、账户设置或发布管理页面。

## 10. 技术架构建议

```text
本地 GitLab（局域网，公开数据仓库）
  ├─ GitLab 既有研发身份和项目权限
  ├─ 工作分支、合并请求和提交历史
  ├─ CI 数据校验
  └─ 受保护 main：正式 JSON 数据和版本清单
                    |
               匿名 HTTPS 读取，同一提交 SHA
                    |

Windows 客户端（本地）
  ├─ 本地已验证快照和来源提交
  ├─ 本地全文/语义索引
  ├─ 参数校验与组帧引擎
  ├─ 售后只读界面
  ├─ 本地草稿录入和导出工具，无应用登录
  └─ 后台同步和本地回滚
```

### 10.1 GitLab 数据源

- 复用本地 GitLab，账号、权限、MR、历史和 CI 均由现有平台承担，无需自建协议数据库服务或发布 API。
- 仓库地址、项目 ID、固定分支 main 和证书信任在客户端部署时配置；售后只关注同步状态。
- GitLab 主机托管沿用现有基础设施；若仍安排在树莓派上运行 GitLab，主机部署能力在 P3 单独确认，不把它当作已完成的部署。
- GitLab 项目、实例和 Runner 的备份与运维按现有流程执行；Git 历史不是服务器故障时的备份替代品。

### 10.2 Windows 客户端

- 可继续使用 Qt 6/C++，与当前团队工具链和绿色包交付方式一致。
- 本地快照保存正式数据，本地数据库/索引保存检索结果、收藏、历史和同步状态。
- 语义检索模型须做 CPU 性能和包体大小技术验证；若设备太旧，全文+同义词仍可降级工作。
- 所有生成结果都携带指令ID、内容版本、来源提交 SHA、适用型号和参数快照，便于复现。

## 11. 公开读取与数据可信性

- **Public 表示对能访问 GitLab 的人开放读取，并不自动把局域网服务器暴露到互联网。** 正式数据仓库只放允许公开给售后的内容；不适合公开的内容也不能放在它的工作分支或历史中。
- 软件不保存研发密码、写入令牌或部署密钥；研发的提交身份和 main 权限归 GitLab 管理。
- 同步使用 HTTPS 并校验服务器证书；内部证书由部署统一配置，不通过关闭证书验证解决访问问题。
- SHA-256 用于确认文件完整性，同提交 SHA 用于确认快照版本一致；它们不替代服务器身份校验，也不证明业务协议一定正确。
- main 权限、CI 验证、维护者审核和客户端复验共同承担数据质量控制。MVP 无需另建签名服务。
- 内容修改和发布追踪使用 GitLab 提交与 MR 记录；客户端保留本地生成/同步历史，无账号模式不承诺逐人集中记录售后导出事件。

## 12. MVP 范围与后续路线

### 12.1 MVP（建议必做）

- 产品/型号/固件/协议档案。

- 与串口测试工具/网络诊断工具深度集成并直接发送。
- 设备自动识别、回读验证、操作编排和现场报告。
- 与公司工单系统衔接指令及现场处理记录。

## 14. MVP 关键验收场景

1. **正常离线**：成功同步后断开所有网络，仍可完成搜索、填参、生成和导出。
2. **同步坏包**：下载中断、哈希错误、证书错误、schema不兼容时，旧版仍可用；首次无快照则明确提示暂无数据。
3. **GitLab 权限**：无需登录可读取公开数据；无写入权限的用户不能更新仓库，研发不能直接推送 main，维护者仅通过规定的 MR 流程合并。
4. **适用性**：不同固件下同名指令有不同帧时，只能生成当前适用版，未选版本时不默认猜测。
5. **数值边界**：亮度为0、999可正确编码，-1、1000被拒绝，语义查询提取的值也不能绕过检查。
6. **编码**：大小端、ASCII定长/补位、缩放和枚举对照黄金向量完全相等。
7. **校验**：算法和覆盖范围任一变更都会造成旧向量失败，阻止发布。
8. **发布回退**：维护者通过 revert MR 恢复正确内容形成新 main 提交，客户端能同步；本地上一份快照也可恢复。
9. **搜索**：“调光”、“设亮度”、“通道3设255”召回正确指令；该型号不支持时明确无结果。
10. **风险命令**：L3 内容不进入公开仓库；L2 按公开发布策略排除或显示警告，不依赖账号隐藏。
11. **变更追踪**：能从客户端记录的来源提交对应到 GitLab 的差异、MR 审查和合并记录。
12. **GitLab 故障**：本地服务器宕机不阻断已同步客户端的使用；恢复后可继续同步。
13. **同期提交**：下载期间 main 更新，所有文件仍来自本次固定 SHA，下一次同步再读取新提交。
14. **CI 门禁**：无流水线、校验失败或必需校验被跳过时不能正常合并；合并前最新内容通过校验。
15. **无需 Git 环境**：未安装 Git、未登录 GitLab 的售后电脑可正常同步；软件不嵌入写入令牌。

## 16. 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 协议知识没有明确负责人 | 系统做出来但数据不可信 | 每个产品/协议指定 owner，无 owner 不发布 |
| 试图一次支持任意协议 | 模型失控，需要执行脚本 | 先覆盖常用类型，特殊编码通过受测算子扩展 |
| 语义检索“看起来很聪明”但选错协议 | 售后使用错误指令 | 先适用性硬过滤，语义只排序，不生成未入库字节 |
| 研发不愿意录入太多字段 | 数据永远停在草稿 | 模板复制、批量导入、默认值、即时预览，发布必填项保持最少 |
| 树莓派或SD卡故障 | 无法发布新版 | SSD、健康监测、每日异机备份、定期恢复演练；本地只读仍可用 |
| main 配置允许绕过 MR 直接推送 | 未校验数据进入正式分支 | 禁止直接推送/force push，核对匹配规则；客户端仍复验数据 |
| CI 没有覆盖实际待合并内容 | 分支单独通过但合并后规则冲突 | 合并前更新 main 并重跑相同验证器，维护者确认最终内容 |
| 多文件逐个从动态 main 下载 | 新旧数据混合、组帧不一致 | 一次同步固定提交 SHA，全部通过后才激活 |
| 公开仓库含受限资料 | 能访问仓库的人可从分支或历史读取 | 公开仓库仅保存可分发数据，受限资料继续使用研发原有存储 |
