# 串口测试工具软件功能需求表 V1.1

## 1. 项目定位

本软件是基于 Qt 开发的 Windows 桌面串口测试工具，用于串口协议调试、指令管理、自动发送测试、丢包率统计和回复正确率统计。

软件第一版以“单条指令循环测试”为核心，不做多指令脚本、不做复杂通配符匹配、不做跨平台适配。

---

## 2. 技术范围

| 项目 | 要求 |
|---|---|
| 开发框架 | Qt |
| 推荐模块 | Qt Widgets、QSerialPort、QJsonDocument、QFile |
| 运行平台 | Windows |
| 测试方式 | 单条指令循环发送 |
| 最小发送间隔 | 1ms |
| 最大发送间隔 | 5000ms |
| 最大自动发送次数 | 10,000,000 次 |
| 回复判断方式 | 第一版只做固定回复精确匹配 |
| BCC 功能 | 任意 HEX 发送均可选择自动追加 BCC |
| 日志策略 | 默认保存统计和异常；用户勾选后保存全量日志 |

---

## 3. 软件总体目标

本软件用于替代普通串口助手，并在普通串口收发功能基础上，增加以下定制功能：

1. 协议指令库管理。
2. 自动发送测试。
3. 丢包率统计。
4. 回复正确率统计。
5. 异常日志记录。
6. 全量日志可选保存。
7. BCC 自动校验追加。

软件应支持把已有的新协议、旧协议、旧扩展协议整理成可视化指令库。用户可以在界面中查看、编辑、添加、删除协议指令，并为每条指令配置发送内容、正确回复内容，用于后续自动测试时判断通讯是否成功。

## 6.5 回复超时规则

### 6.5.1 超时模式

| 模式 | 说明 | 第一版要求 |
|---|---|---|
| 自动超时 | 软件根据发送间隔自动计算回复超时时间 | 默认启用 |
| 手动超时 | 用户自己输入回复超时时间 | 必须支持 |

### 6.5.2 自动超时计算规则

```text
auto_timeout_ms = send_interval_ms × 2
如果结果小于 10ms，则按 10ms 处理
如果结果大于 5000ms，则按 5000ms 处理
```

示例：

| 发送间隔 | 自动回复超时 |
|---:|---:|
| 1ms | 10ms |
| 5ms | 10ms |
| 10ms | 20ms |
| 100ms | 200ms |
| 1000ms | 2000ms |
| 5000ms | 5000ms |

### 6.5.3 超时判断逻辑

每发送一次指令，软件记录该次发送的时间。

如果在超时时间内收到正确回复，则该次发送判定为成功。

如果在超时时间内收到数据，但内容与正确回复不一致，则判定为回复错误。

如果超过超时时间仍未收到回复，则判定为超时，也就是丢包。

## 6.7 统计公式

| 指标 | 公式 | 说明 |
|---|---|---|
| 发送次数 | `send_count` | 实际执行发送的次数 |
| 接收次数 | `receive_count` | 收到回复的次数 |
| 超时次数 | `timeout_count` | 发送后超时未收到回复的次数 |
| 回复错误次数 | `mismatch_count` | 收到回复但内容不符合预期 |
| 匹配成功次数 | `match_success_count` | 收到回复且内容正确 |
| 丢包率 | `timeout_count / send_count × 100%` | 衡量有没有收到回复 |
| 回复正确率 | `match_success_count / receive_count × 100%` | 衡量收到的回复是否正确 |
| 总成功率 | `match_success_count / send_count × 100%` | 衡量整体通讯成功比例 |
| 平均响应时间 | `总响应时间 / match_success_count` | 只统计成功匹配的回复 |

注意：

丢包率主要反映“有没有收到回复”。

回复正确率主要反映“收到的回复内容对不对”。

总成功率反映“发出去之后最终成功的比例”。

# 7. 第一版不实现内容

| 功能 | 第一版不实现原因 |

# 8. 非功能需求

## 8.1 性能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| NFR-001 | 自动发送最大次数 | 软件应支持最大 10,000,000 次自动发送 |
| NFR-002 | 发送间隔范围 | 自动发送间隔支持 1ms~5000ms |
| NFR-003 | 界面不卡顿 | 自动测试期间界面仍可响应停止操作 |
| NFR-004 | 后台线程处理串口 | 串口收发、回复匹配、统计计算应在后台线程完成 |
| NFR-005 | UI 限频刷新 | 不允许每收到一条数据就强制刷新完整界面，建议 100~500ms 刷新一次统计 |
| NFR-006 | 日志不爆内存 | 千万次测试时不能把所有日志保存在内存文本框中 |
| NFR-007 | 计数器使用 64 位 | 发送次数、接收次数、错误次数应使用 64 位整数 |
| NFR-008 | 1ms 定时说明 | Windows + Qt 的 1ms 定时不是硬实时，允许存在抖动 |

## 9.3 UI 刷新策略

测试数据可以实时统计，但界面不要每发送一次就刷新一次。

建议：

```text
后台统计：每次发送/接收都实时更新
界面刷新：每 100ms ~ 500ms 刷新一次
接收窗口：只显示最近 1000 条
完整日志：写入文件
```

这样即使发送 10,000,000 次，也不会因为界面文本太多导致软件卡死。

# 10. 自动测试核心流程

## 10.1 用户操作流程

1. 打开软件。
2. 选择串口和波特率。
3. 打开串口。
4. 进入协议指令库，选择一条指令。
5. 检查发送内容和正确回复内容。
6. 进入自动发送测试页。
7. 设置发送间隔，范围 1ms~5000ms。
8. 设置发送次数，范围 1~10,000,000。
9. 选择是否启用检测。
10. 选择回复超时模式：自动或手动。
11. 点击开始测试。
12. 软件后台自动发送、接收、匹配、统计。
13. 用户查看丢包率、回复正确率、总成功率、错误明细。
14. 测试结束后导出报告。

---

## 10.2 自动测试内部流程

1. 读取当前测试指令。
2. 根据指令配置生成发送字节。
3. 如果启用 BCC，则自动计算并追加 BCC。
4. 记录当前发送序号和发送时间。
5. 通过串口发送数据。
6. 如果检测功能关闭，则只统计发送次数。
7. 如果检测功能开启，则等待设备回复。
8. 在超时时间内收到回复，则进行固定回复精确匹配。
9. 匹配成功，成功次数加一。
10. 匹配失败，错误次数加一，并记录实际回复。
11. 超时未收到，超时次数加一。
12. 更新统计数据。
13. 判断是否达到发送次数。
14. 未达到则等待下一个发送周期。
15. 达到则停止测试并生成结果。

# 13. 重要实现注意事项

## 13.1 关于 1ms 自动发送

Windows + Qt 的 1ms 定时不是硬实时。软件可以支持用户设置 1ms，但实际发送间隔可能会有抖动。

第一版可以把 1ms 作为压力测试功能，而不是保证每次都精确 1.000ms。

影响实际发送间隔的因素包括：

1. Windows 调度精度。
2. Qt 定时器精度。
3. 串口波特率。
4. 单帧发送字节长度。
5. 设备回复速度。
6. UI 刷新频率。
7. 日志写入速度。

## 13.2 关于正确率实时计算

正确率建议实时计算，不建议依赖用户事后手动计算。

实时对比固定回复的 CPU 消耗很低，真正容易影响性能的是：

1. 每条数据都刷新到界面。
2. 每条数据都写入 UI 文本框。
3. 全量日志同步写入文件。
4. 大量日志保存在内存中。

因此应采用以下策略：

1. 后台线程实时统计。
2. UI 定时刷新。
3. 界面只显示最近 1000 条。
4. 默认只保存统计和异常。
5. 全量日志由用户手动勾选后启用。

## 13.3 关于 BCC

第一版 BCC 规则：

1. 仅在 HEX 发送模式下启用。
2. 用户可对任意 HEX 发送内容勾选自动追加 BCC。
3. BCC 计算方式为异或校验。
4. 计算范围为当前输入的所有 HEX 字节。
5. 追加位置为发送数据末尾。

示例：

```text
原始 HEX：CA 01 01 00 FF
自动追加：CA 01 01 00 FF 35
```

其中 `35` 为前面所有字节异或后的结果，具体结果以程序实际计算为准。
