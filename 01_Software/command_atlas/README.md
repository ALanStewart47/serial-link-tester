## 本地数据

`resources/catalog/` 是首版数据格式样例：`manifest.json` 固定 schema 版本和文件关系；`products.json` 声明产品及支持协议；`commands.json` 包含指令模板、检索字段、参数和有序帧段；`synonyms.json` 保存中文同义词。模板帧段仅接受固定值、参数值和受支持的计算字段，不执行脚本。研发录入的模板直接沿用此 schema。

## 人工验收步骤（S1）

1. 启动后应显示示例产品和 12 条指令；切换三种协议时列表相应过滤。
2. 搜索“设置亮度”或“调亮”，应找到亮度设置；搜索“脉冲宽度”应找到脉宽指令。
3. 新协议亮度保持通道 1、值 255，核对 HEX 为 `CA 01 01 00 FF 35`（BCC 对前 5 字节异或）；改通道和值后字节应随之变化。
4. 旧协议亮度默认应为 `SA0255#`，旧扩展亮度默认应为 `$01A0123#`；分别改通道和值确认 A~H 映射和补零格式。
5. 选择读取模板确认只显示通道参数；复制 HEX/ASCII 与导出的文本应和预览一致；通道或数值不能越出字段范围。

用户负责以上界面/协议语义验收。助手只执行 CMake 构建、编译告警和 JSON/资源静态检查，不做设备模拟或复杂自动化测试。

## 人工验收步骤（S2）

1. 启动程序并点右上角“研发录入”，确认出现本地指令草稿编辑器；建立一个新草稿，填写产品、协议、功能分组、中文名称、用途、别名和关键词。
2. 添加一个整数参数（例如 `brightness`，范围 0~255，默认 100，编码 `u8`）；再添加一个参数段。此时新协议因尚未补齐 BCC 而拒绝预览/导出是正常结果。
3. 新协议在参数段前按顺序添加固定 HEX 段（例如 `CA 01 01 00`），并追加末尾 XOR BCC；确认预览字段校验通过，HEX 为 `CA 01 01 00 64 AE`，ASCII 可见。旧协议请用固定 ASCII 段并核对导出格式。
4. 保存后关闭并重新打开“研发录入”，确认草稿及字段仍在；复制草稿后修改副本，原稿应保持不变。
5. 将亮度最大值改成小于默认值，确认参数编辑弹窗拒绝保存；移除仍被引用的参数应被拒绝，删除新协议 BCC 后应停止生成预览并禁用导出。恢复有效配置后导出标准 JSON，确认外层包含 `format`、`schema_version` 和 `commands`；点击左下“导入 JSON…”选取导出文件，核对字段与组帧一致。同ID会分配新ID，其余字段保留，原稿不覆盖。

草稿不会进入售后查询页或修改内置目录。本地导出文件的导入回读属于 S2 验收闭环，不等于 S3 的 GitLab 仓库同步。main 分支同步及离线快照属于 S3，需 S2 用户验收通过后再开发。
